# Release preparation

Draft for maintainer review. This skill describes two steps; it does not install an automated release runner. Do not commit this draft until the maintainer asks.

Use `check [version]` for readiness and note preparation. Use `release <version>` for publication. If the request only says "prepare" or "check", finish step 1 without starting step 2. An explicit release request authorises its stated publication scope; do not ask again for actions already authorised.

Resolve paths from the Ananke root. The documentation checkout is normally its sibling `../documentation`; verify its identity. Read each repository's applicable instructions and the [development reference](../../references/development.md). Read [the backlog](references/backlog.md) before planning checks. Consult [the v2.21 record](references/v2.21-release-record.md) for historical evidence or a matching roadblock, not as a script to replay.

## Step 1: check

1. **Establish the candidate.** Inspect both working trees and current local and remote `main` and `development` refs. Preserve unrelated work. Identify the previous stable theme tag and the requested version; do not derive a version from a note's filename. Record the exact candidate SHAs and the full changes since the previous release, including changes already on development before the latest feature PR.
2. **Run relevant checks.** Run theme quickstart, feature coverage, and the browser tests affected by the release. For navigation and layout changes, cover mobile and desktop sizes, keyboard access, focus, no-JavaScript output, and overflow. Test the declared minimum Hugo version and a verified current release; record the exact binaries used. Check Hugo Module and Git submodule consumers when installation behaviour changes. Do not install tools globally without need.
3. **Keep validation scoped.** Exclude `scratch/` from all linting, compilation, packaging, and error checks. Inspect command scope before invoking aggregate commands such as `npm run check`: the current TypeScript include is broad. Use an equivalent scoped check when necessary, and say which full check was not run. Record baseline failures separately from regressions; do not label the candidate fully passing when a required gate fails. Obtain a maintainer decision on unresolved release blockers unless that decision is already explicit.
4. **Check the documentation.** Match documented parameters, defaults, hooks, precedence, mobile behaviour, image sources, requirements, and upgrade advice to the implementation. Verify renamed-page aliases, internal links, search, option references, and tables on relevant screen sizes. Use local replacement or remote preview selection for unreleased changes; a successful preview does not prove a production build uses that revision.
5. **Prepare the release text.** Use a supplied note path or a specifically named release draft. If no draft exists, create one within the authorised scope. Read scratch notes only when explicitly included in the request, and never lint or run error checks on scratch. Update the prose to cover the complete release range, with a linked contents list, the main user-facing changes first, documentation and upgrade guidance, and contributor/tooling changes last. Use final production documentation URLs; distinguish links that will become live after publication. State only requirements and compatibility changes supported by this candidate. Do not copy historical SASS migration or Hugo-version boilerplate from the old release-notes skill.
6. **Verify the proposed version.** Inspect `.release-it.ts`, its installed configuration package, the previous tag, and Conventional Commits. Run the actual release script with `--dry-run --ci --no-github.comments.submit`. Stable releases require a branch named `main`; if the candidate is still on development, use an isolated disposable clone with local main at that candidate. Do not promote the live branches merely to make a check work. Stop and explain any proposal different from the requested version. A major proposal needs a separate maintainer decision because the module path is `github.com/gohugo-ananke/ananke/v2`; never silently force or publish a major.
7. **Report readiness.** Record the note path, candidate refs, proposed version, tool versions, checks, baseline exceptions, required documentation updates, and outstanding decisions. A check result is evidence for this candidate only. Prepare the concrete release plan before asking for any missing approval. Do not commit, push, tag, merge PRs, alter repository settings, or deploy in check mode.

Useful existing checks include `npm test`, `npm run test:coverage-gate`, and `npm run test:e2e` in the theme, and `npm run test:build` in documentation. Read the current scripts and scoped instructions before choosing the exact commands.

## Step 2: release

Run this step only when the user requests publication and the target version and notes are settled. Check mode alone does not authorise it.

1. **Reconfirm the candidate and scope.** Recheck refs, working trees, source notes, required CI, and unresolved blockers against the readiness record. Rerun checks affected by intervening changes. Confirm whether the request includes documentation publication. Retain both `development` branches throughout.
2. **Promote the theme.** Rebase development onto main as needed, then use a development-to-main PR with a rebase merge. No squash or merge commit for promotion. Verify the resulting tree against the reviewed candidate. Check source-branch auto-deletion before merging; ensure development cannot be deleted. If a temporary setting change is needed within the authorised scope, record its original value and restore it even if a later step fails.
3. **Run the release script on main.** Repeat the dry run on the actual promoted main. Stop if the proposed version changes. Inspect current credentials through the configured token variable without printing or persisting secrets. Use `npm run release -- "$release_version" --ci --no-github.comments.submit` with the settled semantic version and the approved text supplied through the supported `github.releaseNotes` option, using safe command quoting. The script currently updates version/changelog files, commits, tags, pushes, creates the GitHub release, and creates its linked discussion; npm package publication is disabled. Do not replace this process with an ad hoc tag. Do not post issue/PR comments or social announcements unless those are separately authorised.
4. **Verify publication before continuing.** Confirm the exact stable tag, its target commit, remote main, package version, release body, and published rather than draft/prerelease status. If a command fails after changing remote state, inspect what already exists before retrying. Do not recreate or move a published tag. If the text needs correction, update both the release and its copied discussion body, without changing released code.
5. **Resolve and pin the documentation dependency.** Confirm Go can resolve the published `/v2` module tag. Update documentation's checked-in `go.mod` and `go.sum` to that tag, without retaining a feature revision or local replacement. On its reviewed development branch, run `npm run build -- --expect-theme-version "v$release_version"` and relevant checks. Record the actual resolved module and Hugo version. If the resolver returns the old stable tag, stop this phase and retry after availability changes; never publish the old result as the new release.
6. **Promote and deploy documentation.** Only after the theme release is available and the guarded build passes, promote documentation development to main through a rebase PR. Verify tree equality and retain development. Observe the existing main-triggered Netlify production and GitHub Pages deployments. Do not issue a duplicate manual deployment when the automatic one succeeds. If a manual production deploy is required and authorised, use the existing linked site and `npm run deploy:production -- --expect-theme-version "v$release_version"` from main.
7. **Verify the live result and retain the branches.** Confirm deployment state, published source commit, canonical site URL, release links, old URL redirects, search, mobile navigation, and responsive tables as applicable. Keep preview, branch-deploy, and production evidence distinct. Rebase retained development branches onto their released main histories; verify trees and use an exact old-SHA lease for any required shared-branch rewrite. Never delete development.
8. **Close the record.** Report the actual version, release/discussion URLs, production URL, commit/deploy identifiers, branch state, checks, and limitations. Save commands, roadblocks, remedies, and new improvement candidates in the release record and backlog. A source merge, local build, and live deployment are separate outcomes; claim only what was observed.

For restricted environments, prefer writable task-specific caches and process-local transport settings. Preserve checksum verification and global credentials. The [v2.21 record](references/v2.21-release-record.md) explains why a fresh module cache, writable GOPATH, and writable XDG cache can each matter.

## Draft follow-up

Maintain [the backlog](references/backlog.md). It distinguishes implemented release capabilities from manual procedure, incomplete safeguards, and future work. New scripts, workflow changes, or fixes require their own implementation and meaningful validation; this draft does not imply that they exist.
