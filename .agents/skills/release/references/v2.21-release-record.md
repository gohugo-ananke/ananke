## Guidance and automation candidates

* Separate theme promotion, theme publication, module availability, documentation promotion, and live verification into explicit phases. Publication order prevented an old-stable documentation build.
* Always dry-run the actual release configuration, inspect its proposed version, and gate the authorised minor version before any tag/push. A breaking Conventional Commit can propose a major version; stop for the maintainer rather than forcing it silently. The Go module remains /v2.
* Protect long-lived development branches from source-branch auto-deletion. A future promotion workflow should enforce this without temporarily changing the repository-wide setting.
* Use a task-specific writable GOPATH, module cache, Hugo cache, and XDG cache in restricted environments. Fresh Go VCS caches matter after transport failures. Preserve checksum verification and avoid global credential/SSH changes.
* Explicitly update checked-in documentation pins after publication, even when production resolves latest, so ordinary Hugo builds also use the released theme.
* Pass the exact stable tag through a release-to-documentation workflow and use --expect-theme-version. Verify the selected version in CI logs and the published commit/deploy ID separately.
* Use main-triggered deployment once; observe its result instead of running a duplicate manual production deploy. Keep deploy previews, branch deployments, Netlify production, and GitHub Pages evidence distinct.
* Rebase promotion changes commit IDs. Verify resulting trees, retain development, rebase it onto released main, and push shared refs only with an exact-SHA lease. Existing empty integration commits survived the final rebases; they are harmless but make branch history less clear.
* Confirm documented parameter paths against the implementation before publication. If release text is corrected later, update both the GitHub release and its copied discussion body.
* Update the release-notes skill before reuse: its historical mandatory SASS breaking-change and Hugo requirement boilerplate does not describe this release. Do not insert it merely because the skill says so.
* Capture user-facing validation separately from environment failures. GitHub's existing dependency advisory notice appeared during the docs push, but no dependency scope was added to this release task.
